# 定向包 · 技术文档 / 方案 / 报告

> 本场景加权层：组织/篇章（骨架与标题即摘要）、语言层次/语域（读者层级定术语密度）。
> 格式与符号按输出语言读 zh.md / en.md 的格式节。

> 命中条件：产出是给人评审或复现的技术文本（设计文档、方案说明、实验方法段、README、评审稿）。
> 读者用途：**照着做或照着评审** → 精确优先，白话其次。

## 一、这个场景特有的硬要求

1. **可复现性优先于可读性。** 参数、版本、前置条件、依赖顺序一个都不能少，
   哪怕句子变长。宁可句子笨拙，不可信息缺失。
2. **不补步骤。** 原文没写"怎么切分数据""用什么随机种子""在哪一步执行"，
   就**不要**为了"更完整"补上。这是本场景最高频的编造形式。正确做法：列进待补清单。
3. **不补建议。** "复现时需保持一致""建议加索引"这类原文没有的告诫，一律不加。
4. **术语第一次出现要有锚。** 锚只能用原文已有的话；没有就把术语列进待补清单，
   不要引入外部定义。
5. **机制陈述即使空洞也要留。** "该设置能缓解分布偏差"是作者的断言，
   不是空话——删掉等于替他做取舍。
6. **抽象层与实现层同时出现。** 只谈概念会飘，只谈代码会失去设计视角。
   写"改造/补充实现"时给可扫描的块：

   ```
   可能涉及到的补充实现：
   - 存储层 CRUD 拓展
   - 编排从 inline 转向异步消费
   - tracing 压缩与聚合策略
   ```

## 二、待补清单

写法与分级判据见 SKILL.md 的 S7 与 S8，照那里抄。这个场景额外注意：

- 判断与依据必须相邻。判断在第 2 段、依据在第 6 段 = 需要跳读 = 不合格。
- 标题 ≤25 字且承载内容；把各级标题连起来读，应得全文七成信息。
- 待补清单是**加分项不是减分项**：它证明你没有编。
