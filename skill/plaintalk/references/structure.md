# 共用结构层 · 篇章与论证

> 这一层与语言无关，中英共用。管的是信息组织与论证顺序，不是词汇。

## 一、长文骨架（超过 6 个 bullet 或 150 字就必须走）

```
【重点】/【Bottom line】
＜结论一句 + 所以要做的事一句。读者只读这块就能做对决定＞

1. ＜起：现在是什么状况＞
2. ＜承：为什么会这样、影响多大＞
3. ＜转：有哪些选择、卡在哪＞
4. ＜合：建议什么 + 理由一句＞

附：原始细节        附：不确定的地方
```

规则：

- **开头块先给结论，不给主题。** 读者第一秒要拿到答案，不是拿到预告。
- **开头块不放理由、不放过程、不放细节。** 理由放第 4 段，细节放附录。
- **开头块要能单独存活。** 假设读者看完就关窗口——他做的决定还对吗？不对就重写。
- **下面的编号小节是"逐一确认"，不是"重新推导"。**
- **小节一律编号。** 读者要能看到总共几段、现在第几段。附录不编号，
  读者才不会以为后面还有重点没读。
- **标题是一句带内容的话，不是抽象标签。** 把所有标题连起来读，就该懂全文八成。
  - ✗ `1. 现况分析 / 2. 资料层 / 3. 结论`
  - ✓ `1. 栏位被拆一半就停手 / 2. 前端还在读，所以折扣永远是 0 / 3. 建议另开一张卡`
- **标题说出"出了什么事"，不是"这段在讲什么"。**
- **一节最多 3–5 个 bullet。** 超过就是两件事黏在一起，拆成两节。
- **短内容不要硬分节。** 分节是导航，不是仪式。

## 二、论证顺序

默认主线：

```
背景 → 拆解现状 → 提出猜想 → 分节解答 → 回指前文 → 影响面 → 可观测/评测 → 收束
```

证据优先顺序（写技术内容时）：

```
代码 / issue / trace / 指标  →  宏观规律  →  抽象归纳  →  设计判断
```

- 不替读者抢先下判断。"很清楚""说明了""显然""真正"这类词，
  换成三步：**观察到什么 → 能归纳出什么 → 这个归纳适合落在哪**。
- 要给强判断，至少满足一条：前文提过这个猜想（本段是回指）；
  同段有交叉验证的证据；引用了具体模块、代码、issue、trace、指标或实验结果。
- **前文提出的问题，后文必须回应。** 原文没答案就保留为"未决"，不得编。

## 三、行动项的最低完成度

「要处理」不是结论，是空话。每个行动项要有：

**谁** 做、动 **哪个文件／分页／字段／行号**、改成 **什么**。

- ✗ `常数列：要处理`
- ✓ `config/limits.yaml 的 retry_count（永远是 3）：从配置文件删掉，或改代码不要读它 —— 由你决定`

原文缺主语或缺位置时，**不要帮它圆过去**。写"原文没说"并单列一节。
白话化只能把话讲清楚，不能生出原文没有的事实。
